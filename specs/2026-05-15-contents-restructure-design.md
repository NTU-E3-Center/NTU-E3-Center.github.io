# `contents/` folder restructure — design

**Date:** 2026-05-15
**Status:** Approved (pending re-review of this written doc)
**Branch context:** `feat/member-content-restructure`
**Implementation plan:** to be written after this design is approved.

---

## 1. Motivation

The current `contents/` layout has two structural problems:

1. **Source and generated artifacts are intermixed.** `contents/structures/` contains hand-edited site data (`pages.json`, `publications.json`, `news.json`, `research.json`, `group-life.json`, `videos.json`, `about.json`, `contact.json`) *and* gitignored build artifacts (`members.json`, `members/{webId}.json`) regenerated by `excel_to_content.py`. `contents/articles/` has the same split (`about.md`, `contact.md`, `news/{slug}.md` are source; `members-about/`, `members-position/`, `members-interest/` are generated).
2. **Subpage data is fragmented across multiple top-level folders.** The data, prose, and images for the News subpage live in three different places (`contents/structures/news.json`, `contents/articles/news/{slug}.md`, `contents/images/news/{slug}/`). Same for group-life and research. `contents/projects/projects.json` already shows the cleaner per-subpage pattern.

The goal: `contents/` becomes 100% hand-edited source, organized one subpage per folder.

## 2. Goals and non-goals

**Goals**
- Eliminate every gitignored build artifact under `contents/`. After this work, `contents/` contains only files a human edits.
- Group all source for a subpage (data + prose + images) inside one folder per subpage.
- Preserve byte-identical rendered output in `docs/`. The change is invisible to site visitors.

**Non-goals**
- The SEO sweep (separate spec, deferred). Meta-tag refinement, name-variant generator, `news.topics` population, `about.md` headings — none of that is in scope here.
- The build pipeline itself (Jinja2, image conversion, sitemap generation) — unchanged except for path constants and the in-memory handoff.
- Member-facing workflow — the per-member folder convention (`contents/members/{webId}/`) is preserved.

## 3. Architecture after the restructure

```
contents/                          100% hand-edited source
   members/member-info.xlsx
   members/{webId}/member.json + about.md + photo
   {publications,projects,news,research,group-life,about,contact,videos}/*.json + *.md + images
        ↓
   excel_to_content.build_member_data() → Python dict in memory (NO disk writes)
        {
          'members_listing': [...section-grouped roster...],
          'members_by_id':   {webId: {chiNameEng, pubName, position, pageContent, …}},
          'members_md':      {webId: {'about': html, 'position': html, 'interest': html}}
        }
        ↓
   build.py loads each subpage's source JSON/MD directly, merges with the
   excel dict, passes everything to Jinja2 templates.
        ↓
   docs/                            final HTML (output unchanged)
```

Two structural changes vs. today:

1. `excel_to_content.py` becomes a **function** (`build_member_data() -> dict`) instead of a script with disk side effects. Validation still runs; the build still fails on invalid member data; markdown is pre-rendered to HTML inside the function. The function does not write any files.
2. `build.py` no longer globs `contents/structures/`. It uses an explicit per-subpage load list (`publications`, `news`, `research`, `group-life`, `about`, `contact`, `videos`, plus the existing `projects`). Each subpage's data lives at a known path.

One thing this kills: the `pageStructure` and `pageContent.X.content` path strings that `excel_to_content.py` currently bakes into JSON for `build.py` to dereference. Those become direct Python references in the shared dict — no path strings, no file-resolution dance.

## 4. Final folder layout

```
contents/                                100% source
   pages.json                            site-level nav config
   
   members/
      member-info.xlsx                   admin roster (moved from contents/ root)
      member-info.legacy.xlsx            read-only archive (moved from contents/ root)
      MEMBER_TEMPLATE/                   scaffold for new members (moved from contents/ root)
      {webId}/
         member.json
         about.md
         photo.{jpg,png}
   
   publications/publications.json
   projects/projects.json
   
   news/
      news.json
      articles/{slug}.md
      images/{slug}/{0,1,2,…}.{jpg,png}
   
   research/
      research.json
      images/                            (if/when research images exist)
   
   group-life/
      group-life.json
      images/
   
   about/about.json + about.md
   contact/contact.json + contact.md
   
   videos/
      videos.json
      {video files + thumbnails}
```

**Resolution of cross-cutting cases:**

| Case | Resolution | Reason |
|---|---|---|
| `contents/MEMBER_TEMPLATE/` | → `contents/members/MEMBER_TEMPLATE/` | Member-related scaffold; belongs with member sources. |
| `contents/member-info.xlsx`, `*.legacy.xlsx` | → `contents/members/` | Admin roster sits next to per-member folders. |
| `contents/images/home.svg` | → `templates/partials/home.svg` | It is a Jinja2 `{% include %}` template fragment, not data. After moving it, `contents/` no longer needs to be a Jinja2 loader path. |
| `contents/structures/README.md` | deleted | Folder ceases to exist. |
| `contents/projects/README.md` | retained (already source) | Already follows the per-subpage pattern. |

**Folders that cease to exist after Commit 2:** `contents/structures/`, `contents/articles/`, `contents/articles/news/`, `contents/images/`, `contents/images/news/`, `contents/images/group-life/`, `contents/images/research/`. Every image source lives alongside the subpage data it belongs to.

## 5. Migration plan — three ordered commits

Each commit independently leaves `python build.py` working. The contract across all three commits: **byte-identical `docs/` output** vs. the pre-restructure baseline.

### Commit 1 — Eliminate intermediates (no file moves)

Goal: remove gitignored artifacts from `contents/` while the source files stay at their current paths.

- `excel_to_content.py`: top-level script body is wrapped in `def build_member_data() -> dict`. All `os.makedirs` / `json.dump` / `write_text` calls are removed. The function pre-renders the about/position/interest markdown to HTML using the same `markdown` library `build.py` uses, and returns a single dict (shape in §3).
- `build.py`: replace `import excel_to_content` with `from excel_to_content import build_member_data`. Call it explicitly, merge its dict into `structures` and `members_by_id`. Remove the `contents/structures/members/` glob (`build.py:104`) and the `contents/articles/members-interest/{id}.md` lookup (`build.py:257`). The `pageStructure` indirection in `render_member_pages()` is replaced with a direct `members_by_id[webId]` lookup.
- `templates/pages/member/member.html`: where today `about_content[section['content']]` is read with a file-path key, the template instead reads `section['content']` directly (the value is now pre-rendered HTML).
- `.gitignore`: remove the four artifact-dir lines (`contents/structures/members/`, `contents/articles/members-about/`, `contents/articles/members-position/`, `contents/articles/members-interest/`). Delete the actual directories if present locally.
- **Verification:** run `python build.py`, diff `docs/` against a pre-commit snapshot. Diff must be empty (ignoring file mtimes).

## 6. Verification strategy

The single contract across all three commits is **byte-identical `docs/` output**. Procedure:

1. Before starting: `python build.py` on the current `feat/member-content-restructure` HEAD, then `cp -r docs/ /tmp/docs-baseline`.
2. After each commit: `rm -rf docs/`, `python build.py`, `diff -r --brief docs/ /tmp/docs-baseline`.
3. Diff must be empty (image WebP outputs may differ in mtime but not content; verify with `cmp` on a few sample files if `diff` is noisy).

Manual smoke test after Commit 2 (browser): `cd docs && python -m http.server 8000`, then load `/`, `/members/`, `/members/iyunlisahsieh/`, `/publications/`, `/projects/`, `/news/`, an individual news item, `/about/`, `/contact/`. Visual inspection — nothing should appear changed.

If the diff is non-empty at any commit, that's a bug — stop and investigate before continuing.

## 7. Risks and rollback

- **Risk: a stale path reference in CI.** `deploy.yml` runs `python build.py` and deploys `docs/`. It contains no `contents/` path references itself, so the risk is contained to the Python code. Mitigation: the byte-identical-`docs/` test catches it.
- **Risk: `excel_to_content.py` was imported by something else.** It is not (only `build.py` imports it; no `__name__ == '__main__'` runner is needed by anything else). Confirmed by grep.
- **Risk: the legacy Excel `contents/member-info.legacy.xlsx` is referenced somewhere.** It is not (read-only archive, no code reads it).
- **Rollback:** each commit is independent and self-contained. Revert any one to restore the prior state. The branch already exists in isolation (`feat/member-content-restructure`); nothing on `source` is affected until merged.

## 8. Out of scope (deferred)

The SEO sweep we were originally brainstorming — meta-tag refinement, member name-variant generator (heuristic-based, in `seo_helpers.py`), per-subpage `keywords` plumbing, `news.topics` population, `about.md` research-area headings — resumes after this restructure ships, against the new paths. That work has its own design to write.
